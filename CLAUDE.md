# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

drAW2D is a 2D geometry and function plotting app (Canvas, TypeScript + Vite) shipped as a web app, an Electron desktop app (Linux AppImage/deb, Windows NSIS) and an Android app (Capacitor, APK). The UI, command language, test names, commit-facing docs (README, `docs/yol-haritasi.md`, `tests/README.md`) and error messages are in **Turkish** — keep new user-facing strings and docs in Turkish.

## Commands

Node >= 22.12 (`.nvmrc`: 22).

```bash
npm ci
npm run dev              # Vite dev server
npm run typecheck        # tsc for src/ and for electron/ (tsconfig.electron.json)
npm run build            # typecheck + compile electron shell + vite build → dist/, dist-electron/
npm run deploy           # build + upload dist/ to public_html/public/drAW2D (https://madematik.com/drAW2D/) over FTP (scripts/deploy-ftp.mjs, .env; the host has no TLS yet, so .env sets FTP_SECURE=false); add `-- --dry-run` to only list changes. Live site: the user runs it, never run it unasked
npm test                 # Playwright (Chromium); starts Vite dev server on 127.0.0.1:4173
TEST_PREVIEW=1 npm test  # same tests against built dist/ via vite preview (run build first, stop dev server)
BASE_URL=http://127.0.0.1:4174 npm test   # test an already-running server
npx playwright test tests/command-parser.spec.ts          # single file
npx playwright test -g "iç içe matematik"                 # single test by title
npm run electron:dev     # Electron against the Vite dev server
npm run test:electron    # build, then open the app from file:// and check it (needs a graphical session)
npm run dist:linux | dist:win
npm run android:sync     # build + copy dist/ into android/ (Capacitor)
npm run android:apk      # release APK; signed when ANDROID_KEYSTORE, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_ALIAS, ANDROID_KEY_PASSWORD are set
bash scripts/icons.sh    # regenerate every icon from public/img/app-icon.svg: web, build/icons, build/icon.ico, Android (Inkscape + ImageMagick)
```

Playwright uses `/usr/bin/chromium` if present, otherwise `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`, otherwise Playwright's own Chromium. Failure traces/screenshots go to `test-results/`.

## Architecture

The legacy JavaScript engine has been fully replaced by strict TypeScript (`allowJs` is off); touch/pen input, the mobile layout and the Android package are done; iOS waits. The step-by-step migration log was removed; its history is in Git. `docs/yol-haritasi.md` lists suggested features and the user's requests — record new requests there with a date and do not implement any item until the user explicitly asks.

- `src/main.ts` mounts the desktop title bar and calls `startApp` from `src/app/app.ts`, the composition root: it owns the `GeometryDocument`, `ViewportState`, canvas surface and frame renderer, and wires all DOM events. Canvas input is Pointer Events with pointer capture (plus window `pointerup`/`pointercancel` for uncapturable synthetic events): mouse/pen act on press; a touch with a construction tool *aims* (preview follows the finger) and acts on release; a second pointer cancels the single-pointer gesture (reverting a point drag) and starts a pinch (`ViewportState.beginPinch/pinch`, continuous scale). Touch uses larger hit/axis tolerances. Tests that dispatch synthetic input must use `PointerEvent`, and multi-touch tests use CDP `Input.dispatchTouchEvent`. After any model change it calls `refresh()`, which resolves constraints, re-renders cards, updates history buttons and requests one frame.
- `src/app/tools.ts` (`ToolController`): construction tools stage picked points as document drafts and build the final object through the same `prepareCommand` path as typed input (by point/object *name* references), so validation and naming are shared. Clicking a line/circle/tangent/angle creates a point constrained to it. Transformation tools may stage a whole object first; tools that need a typed value (regular polygon sides, radius) return `ToolOutcome.ask`, which `app.ts` answers through `ui/prompt-dialog.ts`. The select tool's drag/pan/axis-drag lives in `app.ts`, as do canvas sliders (`rendering/canvas-slider.ts`: a parameter with `onCanvas` is drawn in screen pixels; its track sets the value, its caption moves it; both are one edit step).
- Appearance: optional model fields `lineStyle`, `labelHidden`, `trace` (absent = default, so reverting a setting restores the exact graph); `size`/`color` already existed. `object-cards.ts` `styleSpec`/`applyStyle` decide which settings a type offers; painters take dash patterns from `rendering/line-style.ts`, and embedded curves (derivative, sectional parts, a tangent's line) are drawn with their card object's style. Traces are app state (`app/traces.ts` `TraceRecorder`: point positions, and for lines/circles/polygons/graphs/curves a copy per change in plane coordinates — graphs as the polylines the plotter drew, recorded through a fake context — passed as `PainterFrame.traces`), not document state. `src/app/object-drag.ts` decides what a select-tool drag moves: a non-derived point, or a whole line/segment/ray/circle/angle/polygon through its defining points when all are strictly free (constructed lines through their source points), or an equation line through its equation, or a plain `function` (no definition) as `f(x − dx) + dy` (`translation` keeps the base expression; the offset is rounded to about a pixel).
- Vector operations: `commands/vector-expressions.ts` reads `u+v`, `2u`, `a*u-v`, `A+u` against the document (the parser cannot see it, so these arrive as `function`/`parameter` commands and `prepare.ts` `vectorResult` takes them when they name a vector). A result is a `vector` sharing the first vector's A, with a hidden tip point carrying a `vectorSum` constraint (terms with numeric coefficients, vectors read live); `updateInPlace` refreshes coefficients when a parameter changes. `vectorExpression` keeps the typed text for cards and is renamed with its names. `u=(3,2)` is `namedCoordinates`: a lower-case name gives a vector from the origin, an upper-case one a named point. Stages 2 and 3 are in `docs/yol-haritasi.md`.
- Grid snapping: on by default, a device preference (`drAW2D.gridSnap` in localStorage, not in files), toggled by the magnet button `#gridSnap`. `coordinate-grid.ts` `snapToGrid` uses the drawn minor step; `pointerInput` adds `ToolInput.grid`, which only `pointCandidate`'s free-point branch reads (existing points and points bound to an object win); drags snap through `ObjectDrag.anchor`, and `leftPress` keeps a trembling press from snapping an off-grid point.
- `src/app/hit-test.ts`: pixel-based tolerance (10 CSS px), nearest wins, points before other objects. `src/app/viewport-state.ts`: pan, cursor-anchored stepped wheel zoom, continuous `zoomBy` (ctrl+wheel trackpad, pinch), axis drag; note the legacy naming where `scaleX`/`unitX` belong to the *vertical* axis. `src/app/object-cards.ts`: all card text (`describeCard`: `input` = definition, `output` = value lines including the name, `valueFirst` = the value is the main row and the definition shows below it only while selected) — card strings are asserted verbatim by tests and fixtures.
- `src/ui/`: `object-panel.ts` reconciles cards by object ID in place (newest first; element IDs `<id>-input`, `<id>-output`, `<id>-sliderA/B`, `<id>-edit`, `<id>-style`, `<id>-settings`, `<id>-color/size/lineStyle/label/trace` are relied on by tests; the root gets `is-active`/`value-first` classes, CSS does the row order and hides the definition row of unselected value cards; an empty output is `hidden`, so the card is one row); `tool-registry.ts` is the single list of tool groups and tools (action, group, icon, label, instruction); `main-toolbar.ts` builds the GeoGebra-style grouped toolbar (when the bar is too narrow, the `overflowActions` buttons — Yardım, Standart Görünüm, Temizle — and then tool groups from the end move into a "⋯" menu, `#moreMenuButton`/`#moreMenu`, re-measured by a ResizeObserver; Dosya, undo/redo, the panel button and the first group always stay; `tests/toolbar-overflow.spec.ts`), the narrow-layout current-tool button and the bottom sheet's tools tab from it, calls `onChange` on selection, and sets `window.drAW2DToolbar` (tests select tools through it; `#mainToolbar[data-action]` shows the active tool). Undo/redo/clear/standard view/help/panel toggle live in the toolbar; plus command input, the math keyboard (`math-keyboard.ts`: inserts at the caret; its action keys dispatch real keydown events so templates/submit behave like the physical keyboard), help popup/suggestions, side panel (a bottom sheet below `NARROW_LAYOUT_QUERY`, 700px; the app starts there with the panel hidden and the origin centered) and toast. `(pointer: coarse)` CSS enlarges touch targets.
- `src/commands/`: input language pipeline. `language.ts` is the single table of the input language: command names/aliases (the parser's `commandKind`), `<Placeholder>` templates for input suggestions (`ui/command-templates.ts`), and help topics/examples (the help popup is generated from it, not written in `index.html`). Add a command there first. `parser.ts` parses a command string (e.g. `Çember((0,0),2)`, `Türev(sin(x))`, piecewise `2x+1,x<0; x^2,x>=0`) into a typed `Command`; `expressions.ts` validates math.js ASTs (rejects unbounded `combinations`/`permutations`/`bignumber`/`fraction`); `prepare.ts` builds all resulting objects atomically **without mutating the document** — a failing command must not consume IDs, names, or history. `names.ts` generates object names.
- Parameters and definitions: `a=2` is a `parameter` object (value/min/max/step). Numeric command arguments are `NumberArgument` (`number | { expression }`); the parser defers unknown names to `prepare.ts`, which substitutes parameter values (`expressions.ts`, `references`/`keepParameters`) so models always hold plain values and the plotter/geometry code stays parameter-agnostic. An object whose values depend on parameters or named functions stores its normalized command in `definition` (created points become name references); `document/definitions.ts` `recomputeDefinitions` re-prepares those in dependency order and `adopt`s the values in place (keeping id/name/color/references, carrying embedded colors so no-op recomputes don't create history). Failed recompute sets `invalid`. Teğet/TeğetH/X/Limit auto-create slider parameters. Card sliders exist only on parameter cards.
- Function analysis: `geometry/analysis.ts` (`curveOf`, `zerosOf`, `analysisPoints`, `definiteIntegral`). Kök/Ekstremum/Dönüm and curve intersections are point sets like intersections (owner + `hideInLabels` helpers, `analysisPoint` constraint with `sourceIds` and a fixed search range), recomputed live in `resolveConstraints` (memoized by curve keys). `onFunction` points follow a graph. `integral` objects compute their value on display.
- Constructions: `geometry/constructions.ts` `constructedLocation` computes `midpoint`, `reflectLine`, `rotate`, `translate` and `lineHelper` constraints (used by `prepare` for initial positions and by `resolveConstraints`). Dik/paralel doğru, kenar orta dikmesi and açıortay are ordinary `lineWithPoints` with a `construction` (for cards) whose B (and for the bisector A) are hidden, unnamed helper points owned via `ownerId`. `ray` and `polygon` are their own types.
- Card editing: `object-cards.ts` `editText` gives each card a parseable `name: definition` text (`describeCard` keeps the display text tests assert). `document/redefine.ts` `redefineObject` splits name/definition, renames (rewriting names in every stored definition), re-prepares the definition and `adopt`s it into the existing object in place; it rejects cycles and, when others depend on the object, incompatible type changes, and matches intersection/tangent helper points by index. The panel's edit mode removes `readonly` only while editing.
- Image objects: `Yansıt/Döndür/Ötele` on a line, ray, segment, vector, equation line, circle, arc or polygon (`prepare.ts` `transformObject`) build an object of the same kind whose points are hidden, unnamed helpers with the transform constraint plus `ownerId`/`pointIndex` (`anchor` helpers stand for an equation line's or radius circle's missing points); `imageOf` records the transformation for cards. A rotation's slider angle is written into the helpers by `definitions.ts` `updateInPlace` (re-preparing would create new helpers); the same function updates parameter-dependent analysis ranges and asymptote ranges. `redefine.ts` matches image helpers by `pointIndex` and swaps the object's own point references to the kept helpers.
- Curves: `implicit` (equation in x and y; `geometry/implicit.ts` marching squares with refined, pole-rejecting crossings, 6 px cells), `inequality` (region; `bound` when one side is y or x alone, shaded by pixel columns), `curve` (parametric/polar, stored in x; `rendering/parametric-plotter.ts`). `rendering/curve-geometry.ts` caches their polylines per expression and view for painting, hit testing and traces. Inequalities are hit only on their boundary so the plane under them still pans.
- Unit circle (`unitCircle`): always at O; its angle is a θ slider parameter (`definition` `{ kind: 'unitCircle', angle }`, kept up to date by `definitions.ts` `updateInPlace`); `show` (ordered parts, absent = only the circle) and `angleUnit` are settings preserved through recompute and redefinition. `object-cards.ts` `setUnitCirclePart` enforces that any value turns A on and A cannot be turned off while a value is shown; the angle's slider is θ's own parameter card (the circle's card has none), dragging A (`object-drag.ts`, `geometry/unit-circle.ts` `angleTowards`, snapping to 30°/45° multiples) also turns θ, and deleting θ deletes the circle. Exact values and quarter-turn exactness are in `geometry/unit-circle.ts`; drawing in `rendering/unit-circle-painter.ts`.
- Analysis point sets grow: `document/point-sets.ts` `growPointSets` adds named members when more solutions appear; `app.ts` `settle()` runs it before every `resolveConstraints`. Members read the owner's search range. Analysis commands accept an expression instead of a function name and create the function first.
- `src/document/dependencies.ts`: `resolveConstraints` recomputes constrained points (`onOther`) in document order (creation order is topological); `collectDependents` drives cascade delete (also via names used in definitions).
- Files: `document/file-format.ts` writes `.drw2` JSON (`{ app: 'drAW2D', format: 1, objects, view }`), shared members as `{ $ref: id }`, and checks types/IDs/references when reading; `app/files.ts` (same as drAW3D) uses the desktop IPC, the File System Access API or download/upload. The autosave (`drAW2D.autosave` in localStorage, 1 s after changes and on `pagehide`) is restored at start with `GeometryDocument.reset` (fresh history); opening a file is one undoable step. SVG export records the painters into `rendering/svg-context.ts` (the grid via `drawGridDirect`).
- `src/document/geometry-document.ts`: object membership, selection, monotonic IDs (never reused), drafts (half-finished tool drawings), and bounded undo/redo (default 100, `historyLimit`) via full-graph snapshots plus a cursor. `graph-equality.ts` compares graphs preserving shared references and distinguishing `NaN`/±Infinity/−0; no-op edits must not create history entries or drop the redo branch. Slider/point drags are one history step; Escape reverts.
- `src/geometry/`: `models.ts` (geometric object classes) and `function-models.ts` (equation/function/analysis objects); name/ID/color generation is injected via callbacks so models stay DOM-free. `primitives.ts`, `intersections.ts`, `tangents.ts` are pure math with no DOM or naming dependencies. Dependent geometry that becomes undefined keeps its last coordinates and is hidden with `geometryValid: false`, then recovers. Coordinates are never rounded in the model.
- `src/math/`: composition, derivative, exact line expressions (`function-algebra.ts`), display formatting. `src/math.ts` configures math.js — pinned at **15.2.0** with a custom `log(base, value)`; don't bump casually. It is created from explicit `*Dependencies` (parse, compile, evaluate, derivative and every function `commands/expressions.ts` accepts), not `all`, and `vite.config.ts` puts it in its own `mathjs` chunk; a new function in the input language must be added in both places.
- `src/rendering/`: `coordinate-transform.ts` is the single math↔CSS-pixel transform shared by drawing and pointer input (DPR applied only at the canvas raster level, no snapping). `frame-renderer.ts` coalesces draw requests into one `requestAnimationFrame`; `coordinate-grid.ts` and `function-evaluator.ts` cache grid and compiled expressions. `function-plotter.ts` takes one sample per pixel, then subdivides only intervals that are curved (chord deviation > 0.5 px), cross the screen or touch undefined samples; it bisects domain boundaries to float precision, extends non-converging boundaries (log, 1/x) to the screen edge as asymptotes, and never joins the sides of a pole/jump found at float resolution. Extra evaluations are budgeted per pixel. `tests/function-plotter.spec.ts` has a coverage/accuracy audit over many functions and zoom levels — keep it passing when touching the plotter. Painters (`scene-painter`, `geometry-painter`, `analysis-painter`, `transient-painter`, `canvas-primitives`) only read a `PainterFrame`; they never touch the document or DOM.
- `electron/main.ts`: shell only. Loads `DRAW2D_DEV_SERVER_URL` in dev, `dist/index.html` in production; `nodeIntegration: false`, `contextIsolation`, `sandbox`. The window is frameless: `electron/preload.cts` (compiled to `dist-electron/preload.cjs`; sandboxed preloads must be CommonJS) exposes only `window.drAW2DDesktop.windowControls` over `window:*` IPC channels and `window.drAW2DDesktop.files` (open/save/export over `file:*`; the main process writes only to paths picked in its dialogs), and `src/ui/title-bar.ts` draws a drAW-style title bar only when that API exists (types in `src/env.d.ts`; the title is `drAW2D | mADEMatik`, no version number). Further OS access goes through the same preload/IPC layer — geometry code must not depend on Electron.
- `android/`: the Capacitor 8 project, copied from drAW3D (committed; `android/app/src/main/assets/public` is generated by `cap sync`). App ID `com.madematik.draw2d` is permanent (Play Store). `app/build.gradle` reads `versionName` from `package.json` and `versionCode = major·10000 + minor·100 + patch` (minor, patch < 100), and signs release builds from the `ANDROID_KEYSTORE*` environment. `DrawFilesPlugin.java` (registered in `MainActivity`) opens and saves through Android's document pickers (drAW3D's copy also prints; drAW2D has no printing); `src/app/native.ts` is its web side plus the back button (`app.ts` `closeSomething`: the tool's question, a toolbar menu, help, the math keyboard, a tool or drag, the bottom sheet, then minimize), saving on pause and opening a tapped `.drw2` file (`VIEW` intent filters: `application/octet-stream` and the `.drw2` path; `appUrlOpen` / `getLaunchUrl` → plugin `read`). Saving asks for the place first (`create`) and writes after (`write`), so a large PNG never sits in the activity's saved state; documents are saved as `application/octet-stream`, or Android appends `.json`. `src/app/files.ts` (same as drAW3D) picks Android before Electron and the browser. The signing key never enters the repository (`*.jks` ignored).
- Icons: the app icon's source is `public/img/app-icon.svg` (the family style: A and W drawn with points and segments, here on axes and a grid; drAW3D's is in a cube); `scripts/icons.sh` generates `app-icon.png`, `favicon.svg`, `build/icons`, `build/icon.ico` and, through `scripts/android-icons.sh`, the Android launcher icons and splash screens.
- Stylesheets are linked from `index.html`, not imported in TS, so the first paint is styled (importing CSS from JS made the 1080px `arrow.svg` flash in dev). Vite `base: './'` so the same build works under `file://`.

## Releases

GitHub Releases is the only place packages are published; madematik.com and the README link to it.

- **Build:** `.github/workflows/release.yml` builds the Linux packages (`.deb`, AppImage) on `ubuntu-latest`, the Windows `.exe` on `windows-latest`, and the signed `drAW2D-android.apk` on `ubuntu-latest` (JDK 21; secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`; missing secrets fail the job, so the release is not published). Never cross-build Windows from Linux (wine) and never upload or replace release assets by hand. Before packaging the Linux job runs `npm test` (Playwright; the workflow installs Chromium). A failing step blocks the release.
- **Version:** `package.json` is the single source, so the local and GitHub versions are always the same. New release: `npm version patch` (or `minor`), then `git push --follow-tags`. The workflow fails if the tag `vX.Y.Z` differs from `package.json`.
- **Rebuild without a new version:** Actions → "Sürüm paketleri" → Run workflow replaces the assets of the current version (creates the release if missing). Build only, nothing published: `gh workflow run release.yml -f yayinla=false`, then `gh run download --name paket-Windows -D release`.
- **Asset names have no version:** `drAW2D-linux-amd64.deb`, `drAW2D-linux-x86_64.AppImage`, `drAW2D-win-x64.exe`, `drAW2D-android.apk` (`build.artifactName` is `${productName}-${os}-${arch}.${ext}`), so `https://github.com/200709078/drAW2D/releases/latest/download/<name>` always fetches the newest release; the README "İndir" section and madematik.com use these links. Don't add the version back.
- **Notes and checksums:** `scripts/release-assets.mjs` writes `SHA256SUMS.txt` and the Turkish release notes (sizes, DEB dependencies and installed size read from the packages). Change the notes in the script, not on GitHub — the next run overwrites them.
- **Local copy:** `npm run dist*` output is for local testing only and differs byte-wise from the published files. To make `release/` match GitHub: `rm -rf release && gh release download vX.Y.Z -D release`, then `sha256sum -c SHA256SUMS.txt` inside `release/`.
- **Shared files:** the workflow and `scripts/release-assets.mjs` are identical copies in drAW, drAW2D and drAW3D (app name and version come from `package.json`) — change all three together. The Android job skips itself in a project without `android/` (all three have one since 2026-10-25). Actions: `checkout`/`setup-node`/`upload-artifact` v7, `download-artifact` v8 (Node 24).
- **Trigger quirk:** push a new or changed workflow file before the tag; a tag pushed in the same push as a new workflow did not trigger it.
- **Metadata:** license MIT (same text in all three repos), deb `Section: education`, `.desktop` categories include `Education`.

## Tests

All tests are Playwright specs in `tests/`. Many (`command-*`, `geometry-*`, `function-*`, `coordinate-*`, `frame-renderer`, `app-tools`, `app-view-cards`) import `src/` modules directly and run without a page; `*-integration.spec.ts`, `migration.spec.ts`, and `rendering.spec.ts` drive the UI. `tests/fixtures/legacy-command-*.ts` hold expected card outputs originally measured from the pre-migration app — they are not sacred: when behavior is intentionally improved, update the fixture with a justification. Object colors are random, so canvas tests check that pixels change/reset rather than screenshot comparisons; use deterministic criteria (frame counts, cache hits) instead of timing.

## Migration conventions

- Port modules with real data/event types; don't just rename `.js`→`.ts` or add `@ts-nocheck`.
- Don't try to preserve existing code. Rewrite or redesign modules, algorithms and behavior whenever that makes them more efficient, correct or usable; the change must be tested and explained.
- After each migration step is completed and verified, stop and wait for the user before starting the next one. Remaining: iOS packaging, once the need is clear.
- `dist/`, `dist-electron/`, `release/` are build outputs and not committed.
